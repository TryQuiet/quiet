# Production QSS and website desktop 9.0.2

**Result: fresh community registration and joining through production QSS fail.**
The server is reachable, but its server-key response is incompatible with the
website's 9.0.2 client. CAPTCHA succeeds; the subsequent setup failure causes
CAPTCHA to appear again. No staging or production deployment was changed.

## Actual client and transport

On September 14, 2026, the Linux download at https://tryquiet.org/ linked to
`Quiet-9.0.2.AppImage`. Its SHA-256 matched the published GitHub asset digest:
`0914284dcec16ec59e03eebe5f96633d81cd4f876a775c596fa6f63fcde40bdd`.
The extracted Electron executable and `app.asar` matched that verified asset.
Its packaged configuration enables QSS at
`wss://qss-prod.quiet-services.app`.

The unchanged application ran twice through the real desktop UI, with fresh
owner and joiner profiles and normal production CAPTCHA verification. Each
client had a separate display. A private mount namespace wrapped the original
Tor executable to append `--DisableNetwork 1` from startup. Both live Tor
processes were observed with that setting; neither completed bootstrap. The
9.0.2 backend/desktop source contains no `DisableNetwork` override. The host's
Tor executable remained unchanged after cleanup.

Production TCP 443 and HTTPS `/health` worked; `/health` returned HTTP 200 with
Postgres up. A separate Socket.IO probe restricted to WebSocket transport also
connected and received a successful `get-captcha-site-key` response. ICMP ping
received zero replies to two packets. Ping does not test the QSS transport, and
these observations do not establish which network layer filters ICMP.

## Captured failure

The owner completed CAPTCHA at approximately 19:58:13 UTC. Unfiltered
ChromeDriver output captured Socket.IO request/acknowledgment packets; the
ordinary E2E log filter dropped some packets when they shared a chunk with
ChromeDriver protocol output. Only field names and statuses are retained here.

| Operation | Production response | Client result |
| --- | --- | --- |
| `verify-captcha` | `status: success` | CAPTCHA accepted |
| `generate-public-keys` | `status: success`; payload contains only `keys` and the matching `teamId` | Rejected: required `serverId` and `identityKeys` are absent |
| Retried `generate-public-keys` | `status: error`, `Captcha verification required` | CAPTCHA opens again |
| `create-community` | No request emitted | Community never registered |
| Joiner's `sign-in-community` for the same team | `status: not found`, `No community found` | Remains joining; no channel appears during the 90-second onboarding wait |

In the exact release source, commit
`f8b35679f38f3970f1c56e8070309b3d71d11d4c`,
`packages/backend/src/nest/qss/qss.service.ts` rejects a server-key response
without `serverId` or `identityKeys` before sending `create-community`.
Its fallback log message, `Response was nullish`, is misleading here: the
captured response was non-null and had status `success`, but required fields
were missing.

This explains successful CAPTCHA answers followed by repeated challenges and
a joiner receiving `No community found`. A Tor-capable joiner may still connect
directly to its peers; that does not establish successful QSS registration.
The user-supplied log shows the same QSS join error, but this test does not prove
how that particular existing community became absent from QSS.

## Scope and validation

The latest successful [production deployment workflow](https://github.com/TryQuiet/quiet-storage-service/actions/runs/28276364963)
released QSS `v1.1.1`, commit `9c0c9154d2991638d886428918f9772e8ddb81f4`,
and completed June 27 at 03:31:02 UTC (June 26, 8:31 p.m. Pacific).
The latest successful [staging deployment workflow](https://github.com/TryQuiet/quiet-storage-service/actions/runs/30122435028)
released `v1.1.2-alpha.1`, commit `731bdd14c14d0185fd0f00def04d8ec16e064c87`,
on July 24. Two old failed runs have September 12 metadata-update timestamps,
but their jobs ran in August 2025; they do not establish later deployments.
These are workflow records, not an independent inspection of the live EC2
revision. Direct AWS inspection was unavailable without configured credentials.

This is a negative functional result for **fresh Linux desktop 9.0.2 communities**
against the deployed production endpoint. Message delivery could not be tested
because QSS registration and joining failed first. It does not establish the
status of every existing community, reproduce 9.0.0 specifically, or identify
the exact deployed server commit. A compatible server/client combination still
needs to be verified before claiming this production path works.

The peer helper now accepts production environment overrides, joins an existing
invitation, allows time for real CAPTCHA, and optionally captures unfiltered
driver output in its private evidence directory. The owner and joiner runs
exercised these paths. Two automated tests additionally launch real child
processes and verify that explicit diagnostic settings, including an empty
`DEBUG`, and production CAPTCHA flags survive the spawn boundary. Both pass;
the helper syntax check, changed TypeScript formatting, and ESLint checks also pass.

All test-owned application, Tor, driver and display processes were stopped and
verified absent. Private logs, screenshots, invitations and profile-path records
remain under `.connection-runs/prod-qss-check/`; profiles retain private
permissions at the packaged app's normal data location. No private packet
contents or invitation credentials are included in this report.

The [sanitized measurements](prod-qss-2026-09-14.json) accompany this report.
These findings are separate from publishing documentation PR #3533.
