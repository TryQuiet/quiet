# Physical iOS alpha against staging and compatible QSS

The published iOS `10.0.0-alpha.0` cannot authenticate to its configured staging
QSS because the server speaks auth protocol 3 and the client requires protocol 4.
The same application successfully joined and exchanged messages through an
isolated QSS built from the alpha's pinned server revision. Stored messages were
delivered in both directions with the sending peer stopped before the receiving
peer started. No client runtime change was needed for these successful tests.

**No staging or production deployment was changed.** The tested remedy is to
align the server's auth protocol with the alpha. Deploying that revision, checking
its migrations and configuration, and repeating these checks on staging remain
separate work. Do not downgrade or bypass the client's protocol check.

| Configured staging endpoint | `wss://qss-dev.quiet-services.app` |
| Compatible QSS commit | `4227d340397135b120fd96a80f7538592ef520c5` |
| Client and compatible QSS auth commit | `6f534c89bceb875e8c71997943e5e76e48ccbd88` |
| Desktop peer | Published Linux `10.0.0-alpha.0`, isolated profile and display |
| Local server | Task-owned QSS, Postgres and Redis fixture on port 3310 |

The IPA was development re-signed for this phone. Its backend bundle, frontend
bundle, `Env.plist`, and `Info.plist` hashes remained identical to the published
artifact. The [sanitized receipt](ios-qss-2026-09-14.json) records those hashes.
The app used real staging hCaptcha verification. The isolated server used the
fixture's public hCaptcha test keys and real verification; push was disabled.

For the compatible-server join, only the invitation's QSS endpoint was changed
to the Mac's Wi-Fi address. A task-owned TCP relay and SSH reverse tunnel carried
traffic to the local fixture. The app's built-in staging configuration and code
were unchanged. WebDriverAgent controlled the phone directly over Wi-Fi.

## Observed results

| Check | Deployed staging | Isolated compatible QSS |
| --- | --- | --- |
| Socket connection | Passed | Passed |
| Auth handshake | Failed repeatedly: protocol 3 versus 4 | Passed |
| Community action | Created locally; QSS writes queued | Joined desktop-created community |
| Live messages | Not attempted after auth failure | Both directions received |
| Stored messages, other peer stopped | Blocked by auth failure | Both directions received |

On staging, the socket connected at `18:42:29.196Z`, CAPTCHA succeeded at
`18:42:32.482Z`, and the server's identity fields were accepted. The phone then
received `REQUEST_IDENTITY` messages containing `protocolVersion: 3`, at
`18:42:45.887Z` and `18:42:47.345Z`. Both ends rejected the handshake with
`PROTOCOL_VERSION_UNSUPPORTED`. QSS log-entry writes, including channel setup,
were queued because authentication never reached the connected state. A locally
visible community therefore did not establish a working QSS connection.

On the isolated server, the phone logged `Auth connection established with QSS`
at `18:50:28.719Z`. It displayed the expected community and `#general`. Fresh
unpredictable messages were sent and their exact text was observed on the other
device in both directions.

The stronger delivery checks excluded Tor as the delivery source:

1. Terminated Quiet on the iPhone and verified WDA app state `1` (not running).
   Sent a previously unseen message from desktop. The fixture held eight log
   entries, with maximum sync sequence eight. Stopped desktop and verified all
   its owned processes exited. Launched the phone at `18:59:32Z`; the exact
   message was visible by `18:59:54Z` with desktop still stopped.
2. With desktop still stopped, sent a new message from iOS. Verified its exact
   local text and that the fixture advanced from eight to nine log entries and
   sync sequence nine. Terminated Quiet on the phone and verified it was not
   running. Launched desktop and passed its exact-message assertion for the
   iOS sender. Rechecked that the phone remained stopped.

These are functional checks, not connection-speed measurements. The observation
times include manual orchestration and should not be used as latency results.

## Cause and scope

Auth commit [`b59a21066`](https://github.com/TryQuiet/auth/commit/b59a21066b461478a5281d0f6b86668993c8f5fc)
changed the connection protocol from 3 to 4 while disabling removal and key
rotation. Version negotiation deliberately rejects peers with different
authorization rules. Quiet 9.0.2's pinned client auth revision
`742ea3dad6d07d54d745fc61b3afd72f5f2a2b59` declares protocol 3; the alpha declares
protocol 4. This establishes a relevant 9-to-10 compatibility change without a
full application bisection.

The protocol failure is shared client/server logic, not an iOS transport defect
or Tor timing variation. Physical iOS 9 was not tested here, so this does not
resolve reports of iOS 9 failure. Staging's exact running commit was not
established: the observed wire protocol is stronger evidence than its last
recorded GitHub deployment, which may not reflect the current process.

The successful comparison does not validate production, cloud deployment hooks,
push notifications, existing-community migrations, or staging after an upgrade.
Staging community creation and isolated-server joining exercised different
onboarding paths; the common auth failure and actual stored-message delivery
are the decisive evidence for this compatibility issue.

The newer-server logs also contained transient storage-close, early auth-sync,
and sign-in errors during onboarding/restart. Authentication and delivery
subsequently succeeded; these logs are retained, not counted as a clean-log pass.
Two desktop send helpers reported false failures because their configured
mixed-case username differed from the app's normalized lowercase username. Both
messages were actually sent and independently verified by exact text on the
iPhone; the raw failed helper responses are retained. Receive assertions used
the lowercase iOS username and passed.

## Repeating the checks

Follow [the comparison protocol](../IOS-QSS-PROTOCOL.md). Download the exact IPA
from the recorded workflow, verify its endpoint and payload hashes, and use a
preserved or fresh test profile. For staging, create a task-owned community with
the server option and inspect the auth handshake after real CAPTCHA succeeds.
Keep logs containing keys and invitations private.

For the isolated comparison, use
`packages/mobile/scripts/qss-e2e/fixture.py` with the pinned QSS and nested auth
commits above. Launch `scripts/connection-regression/desktop_peer.cjs` with a
fresh profile, a lowercase test username, and the fixture endpoint. Join using
the real iOS UI and the invitation's reachable fixture address. Use the peer's
`send`, `wait`, `stop`, and `launch` requests plus WDA app termination/state checks
to repeat both stored-message sequences. Read aggregate storage evidence with
the fixture's `storage` command before starting the recipient.

Raw evidence stays under `.connection-runs/ios-qss/` in this worktree and the
task-owned `quiet-connection-regression-ios` directory on the Mac. The original
Quiet 8 Documents directory was backed up before installing the alpha, and its
backend directories were retained. The alpha is left installed and stopped
with the test profile. The temporary desktop peer, fixture and Mac test services
were stopped after evidence capture.
